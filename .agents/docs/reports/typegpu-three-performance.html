TypeGPU bridge performance

The experimental @pmndrs/glyph/three/typegpu entry now matches the native TSL entry on frame time and builds its materials as fast or faster. Before, it matched on frame time but spent 1.3–4× longer than TSL building each material. The fix is a new way of calling TypeGPU from TSL: each function is compiled once per backend and called with arguments, instead of being recompiled for every material.

Branches claude/glyph-typegpu-perf-mrfm7w in iwoplaza/glyph and iwoplaza/TypeGPU. Measured with the new benchmark:three-shader-performance workflow in Chrome 149 on SwiftShader (no GPU in the container).

Frame is wall time from submit to a completed one-pixel readback. First build is NodeBuilder time for the page's first materials. Warm build is NodeBuilder time after every text is replaced once the page is warm, which is what an application pays for each new text style or font. First frame includes node building, pipeline creation and uploads.

The WebGL2 Bitmap cell is the only one above 1.07 for build time, and it is a roughly 10 ms quantity. A focused 12-round rerun of that cell measured 1.06 for the first build and 1.07 for the warm build, which is parity.

SwiftShader runs shaders on the CPU, so frame times compare relative shader cost, not hardware budgets. Two runs of identical shaders differed by up to 7% per cell, so frame ratios between 0.93 and 1.07 are parity. Build times are CPU work and do not depend on the rasterizer.

Why the original entry was slower

The measurable gap was CPU time spent building materials. Frame times were already within noise of TSL on SwiftShader, whose LLVM backend inlines and deduplicates the repeated pure work described below. Drivers that do less of that would pay for it on the GPU, so the generated code was fixed as well.

Every reuse recomputed the bridge

toTSL returned a plain Three Node. Three only caches a reused result in a temporary for TempNodes, so each use of a bridged value re-emitted every private-variable assignment and called the function again. The original Bitmap fragment shader called the texel-coordinate function twice and assigned its inputs five times: 

var_1 = NodeBuffer_980.value[ nodeVar4 ];
var_2 = NodeBuffer_982.value[ nodeVar4 ];
var_3 = nodeVarying5;
var_1 = NodeBuffer_980.value[ nodeVar4 ];   // repeated for every use
…
nodeVar5 = vec2<i32>( i32( item_1().x ), i32( item_1().y ) );

MTSDF was worse: its coverage and composite results were read four times each, and each read ran the whole chain again, including both texture samples.

Every material recompiled TypeGPU

A toTSL closure captures the material's own TSL nodes, so nothing can be shared between materials. Each material ran the TypeGPU compiler at least twice per stage: once in Three's analyze pass (repeated for every usage of the node) and once to generate code, plus one more resolution per bridge-variable assignment. In a warm page the TypeGPU Bitmap material took about 30 ms to build against 8 ms for TSL. The profile showed no single hotspot, only TypeGPU's AST-to-WGSL generator and garbage collection.

What changed

In @typegpu/three (patched here, committed upstream)

  • toTSL nodes extend TempNode, analyze their function once per stage, and resolve each bridge-variable name once. Reused results are now computed once, and the per-usage recompilation in the analyze pass is gone.
  • New toTSLFn(fn) wraps a shelled tgpu.fn. It is resolved once per backend into one shared namespace, its declarations become shared code nodes emitted once per shader, and TSL values are passed as ordinary call arguments. Identifiers get a _tsl suffix so they cannot collide with toTSL's per-shader names.
  • New handle(type) declares a texture that a function reaches through a slot instead of a parameter. Each call binds its own TSL texture, and only the declarations that read a handle are specialized per binding.
  • prewarm(backend) resolves a function ahead of the first shader build.

The glyph workspace applies these as patches/@typegpu__three@0.12.1.patch, generated from the upstream source in the TypeGPU branch (commits 9f22980 and ef18a43, 26 passing tests).

In glyph

  • The Bitmap, MTSDF, decoration and Slug adapters call the canonical /shaders/typegpu functions through toTSLFn. The canonical shader code is unchanged.
  • Slug keeps its public texel slots and binds them to three handles. One resolved program is cached per page-width triple, since widths are compiled into the texel addressing.
  • defineThreeConfig schedules an idle-time prewarm: WGSL first when navigator.gpu exists, then GLSL, one technique per idle callback.

Rendered output is unchanged. Lit-pixel counts match the original TypeGPU entry in every cell, the benchmark:v1-bitmap --typegpu proof returns the same pixels on WebGPU and WebGL2, and the glyph package test suite passes.

What TypeGPU could improve

Ordered by how much each would have saved this integration.

  1. Make a parameterized bridge the default way to call TypeGPU from TSL. toTSL's closure model forces a full recompilation per material, because the captured nodes differ. toTSLFn shows the alternative: compile once per program, pass values as arguments, cache results like any TSL node. After adopting it, glyph's warm material builds became about 2–5× faster than native TSL for MTSDF and Slug. Upstreaming it (the TypeGPU branch is ready for review) is the single largest improvement.
  2. Precompile at build time. The first TypeGPU resolution in a page is dominated by cold JIT: about 50 ms for MTSDF's six small functions on this machine. unplugin-typegpu already sees every 'use gpu' function, so it could emit resolved WGSL and GLSL for shelled functions whose externals are static and let toTSLFn skip the runtime compiler. Glyph currently hides this cost with an idle-time prewarm, which only works when the application has idle time before its first frame.
  3. Report declaration dependencies. With a shared namespace, resolveWithContext returns only newly emitted declarations and no edges between them. The bridge has to find each declaration's dependencies by scanning its code for known identifiers. A dependencies list on ResolvedDeclaration would make this exact.
  4. Let namespaces reserve names or add a prefix. Keeping bridge names away from toTSL's and Three's names currently takes a regex rename of every declaration. A namespace({ reserved, prefix }) option, or public access to the taken-identifier set, would remove it.
  5. Make resources bindable per call. WGSL allows textures as function parameters, but a slot cannot close over a parameter, so Slug's slot-based loaders needed the handle() placeholder and per-binding specialization. First-class resource slots, bound at the call site, would let hosts keep slot-based APIs without that machinery.
  6. Fix two @typegpu/gl gaps. GLSL struct declarations come back from resolveWithContext without a name, although WGSL ones have it. A texture_2d_array function parameter emits invalid GLSL: the WGSL type name texture_2d_array<f32> and a texelFetch with a separate layer argument.
  7. Make glOptions() reusable or fail clearly. Reusing one options object for two resolutions throws "Cannot initialize shader generators twice", which is easy to hit when resolving an entry and then its identifier.
  8. Allow struct returns across the bridge. toTSLFn only returns scalars, vectors and matrices, so glyph wraps struct-taking canonical functions (msdfCoverageFromDistances, msdfComposite, slugRenderWithOptions) in flat-parameter shells. Mapping TypeGPU structs to TSL structs would remove these wrappers.
  9. Speed up the code generator. Warm resolution still allocates heavily; garbage collection took about 29 ms of one warm rebuild profile. Reducing snippet and string churn in the generator would help every host, not only Three.

Open items

  • Publishing is blocked on upstream. toTSLFn, handle and prewarm are not in a published @typegpu/three yet. The patch only applies inside this workspace, so the peer floor must be raised to the release that ships them before /three/typegpu is published.
  • Bitmap sampling differs between entries. Native TSL samples the Bitmap page through a linear sampler, while the TypeGPU functions fetch the nearest texel. This predates the change and explains the different lit-pixel counts; which one is intended is a separate decision.
  • Hardware GPU numbers are still needed. The presentation workload matrix could not run in this container: SwiftShader drops its instance under that workload for native TSL as well. Frame-time parity should be confirmed on real hardware with benchmark:three-shader-performance.
